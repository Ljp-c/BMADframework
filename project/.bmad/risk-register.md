# 风险寄存器（Risk Register）

> 本文档用于系统地识别、分析、跟踪和缓解项目风险。风险应该定期（周度/月度）更新和审视，确保风险控制的有效性。

---

## 📌 概览

**目的**:
- 识别可能影响项目的潜在风险
- 评估风险的可能性和影响程度
- 制定风险缓解措施和应对计划
- 分配风险应对的责任人
- 定期监测风险状态，及时调整策略

**使用指南**:
- 在项目启动和各个阶段定期进行风险识别
- 风险应在发现时立即记录
- 按可能性 × 影响程度排序风险优先级
- 根据风险等级制定不同的应对策略

---

## 🎯 风险等级定义

### 可能性等级 (Probability)

| 等级 | 含义 | 百分比 | 说明 |
|------|------|--------|------|
| **Very High** | 非常可能 | 75-100% | 几乎肯定会发生 |
| **High** | 很可能 | 50-74% | 很有可能发生 |
| **Medium** | 中等 | 25-49% | 有一定概率发生 |
| **Low** | 不太可能 | 5-24% | 发生的可能性较小 |
| **Very Low** | 极不可能 | 0-4% | 几乎不会发生 |

---

### 影响等级 (Impact)

| 等级 | 含义 | 业务影响 | 时间影响 | 成本影响 | 声誉影响 |
|------|------|----------|----------|----------|----------|
| **Critical** | 灾难性 | 项目失败 | 延迟 > 3 个月 | > $100K | 严重声誉损伤 |
| **High** | 严重 | 核心功能受阻 | 延迟 1-3 个月 | $20-100K | 明显声誉影响 |
| **Medium** | 中等 | 部分功能影响 | 延迟 1-4 周 | $5-20K | 有限声誉影响 |
| **Low** | 轻微 | 非关键功能受影响 | 延迟 < 1 周 | < $5K | 基本无声誉影响 |

---

### 风险级别 (Risk Level)

通过 **可能性 × 影响程度** 计算风险等级：

| | Critical | High | Medium | Low |
|--|----------|------|--------|-----|
| **Very High (75-100%)** | 🔴 Critical | 🔴 Critical | 🟠 High | 🟡 Medium |
| **High (50-74%)** | 🔴 Critical | 🟠 High | 🟠 High | 🟡 Medium |
| **Medium (25-49%)** | 🟠 High | 🟠 High | 🟡 Medium | 🟡 Medium |
| **Low (5-24%)** | 🟠 High | 🟡 Medium | 🟡 Medium | 🟢 Low |
| **Very Low (0-4%)** | 🟡 Medium | 🟡 Medium | 🟢 Low | 🟢 Low |

## 🗂️ 风险分类

| 类别 | 说明 | 例子 |
|------|------|------|
| **技术风险** | 技术选择、实现难度、技术债 | API 服务中断、技术方案不可行 |
| **资源风险** | 人力、技能、工具的不足或流失 | 核心人员离职、技能缺陷 |
| **进度风险** | 时间计划不合理、里程碑可能延迟 | 需求变更频繁、评估不准确 |
| **质量风险** | 产出物可能不符合质量目标 | 测试不充分、缺陷遗漏 |
| **外部风险** | 项目范围外的因素影响 | 第三方服务故障、政策变化 |
| **业务风险** | 商业模式、市场、竞争相关 | 市场需求下降、竞品威胁 |

### RISK-002: 需求变更频繁，影响交付进度

| 项目 | 内容 |
|------|------|
| **风险类别** | 进度风险 |
| **优先级** | 🟠 High |
| **可能性** | Very High (75-100%) |
| **影响** | High (延迟 1-3 个月) |
| **发现日期** | 2024-03-01 |
| **应对负责人** | 产品经理 + 项目经理 |

**风险描述**:
初期需求不够明确，业务方对需求的理解可能变化，导致频繁的需求变更，影响开发团队的计划和生产效率。

**触发条件**:
- 用户反馈与初期需求不符
- 市场竞争压力要求快速调整方向
- 业务目标变化，优先级调整

**当前措施**:
- ✅ 进行了详细的需求分析和评审
- ✅ 建立了变更控制流程
- ✅ 进行周度需求评审，保持与业务方的沟通

**缓解方案**:
1. **冻结核心需求**:
   - 确定 MVP 必需功能，确保不变更
   - 将可选功能推迟到 v1.1 版本

2. **优化变更流程**:
   - 每周只接受一次变更请求
   - 变更需要经过评估，了解对进度的影响
   - 执行变更 = 计划调整 (时间/范围权衡)

3. **增进理解**:
   - 与业务方定期同步 (周度演示)
   - 早期原型验证，避免大错的需求理解

**应急预案**:
- 如果频繁变更导致进度严重滑坡，执行"功能冻结"
- 推迟非关键功能到后续版本
- 根据变更范围重新评估时间表

**监测指标**:
- 每周变更请求数量 (目标 <= 2 个)
- 变更导致的计划调整时间
- Team 的稳定性评分

**状态**: Active | 进度: 60% | 下次评估: 2024-04-01

- Agent 之间产出物格式不一致

   - 建立产出物评审机制

2. **清晰的协作流程** (第 2 周):
   - 绘制端到端的工作流程图
   - 定义每个环节的 SLA（如设计在 3 天内完成）

   - 周度协作评审，检查卡点

- 对问题 Agent 进行专项培训和辅导

**监测指标**:
- 产出物首次通过率 (目标 >= 80%)
- Agent 间平均沟通次数 (目标 <= 2 次)
- 任务完成周期 (目标 <= 原计划 10%)

**状态**: Active | 进度: 40% | 下次评估: 2024-04-08

**风险描述**:

- 文档与代码不一致
- 新成员的学习成本增加
- 调试和维护困难

**触发条件**:
- 重大代码变更没有更新文档
- 缺乏文档更新的规范和流程
- 没有自动化工具检测文档过期

**当前措施**:
- ✅ 制定了文档规范
- ✅ 集成了 API 文档自动生成工具

**缓解方案**:
1. **自动化文档生成**:
   - 使用 Swagger/OpenAPI 自动生成 API 文档
   - 使用代码注释工具生成代码文档
   - 减少手动维护工作量

2. **建立更新规范**:
   - 代码变更必须同步更新相关文档
   - Code Review 时检查文档更新
   - 文档也作为代码变更的一部分

3. **定期审视**:
   - 月度文档审核，检查过期内容
   - 用户反馈时同步更新相关文档

**应急预案**:
- 如果发现大量文档不一致，进行文档重建
- 指派专人负责知识库的日常维护

## 🔄 风险管理流程

### 1. 风险识别 (Identification)
- **时机**: 项目启动、阶段评审、定期风险工作坊
- **参与人**: 全体团队成员
- **输出**: 新识别的风险列表

### 2. 风险分析 (Analysis)
- **时机**: 识别后立即进行
- **参与人**: 相关领域专家
- **输出**: 风险评分和优先级

### 3. 风险响应规划 (Response Planning)
- **时机**: 评估后立即规划
- **参与人**: 风险负责人 + 相关团队
- **输出**: 缓解方案和应急预案

### 4. 风险监测 (Monitoring)
- **时机**: 持续监测，定期审视
- **频率**: 周度 (Critical)、双周度 (High)、月度 (Medium/Low)
- **输出**: 风险状态更新

### 5. 风险控制 (Control)
- **时机**: 当风险发生时立即激활应急预案
- **参与人**: 风险负责人 + 应急团队
- **输出**: 事件处理和恢复
