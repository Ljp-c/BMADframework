## 第三轮对话：架构设计原则

### 话题：核心设计原则

**Architect**: 我定义了以下架构设计原则：

**1. 单一职责原则 (SRP)**

每个模块、服务、函数只负责一个功能。

**应用**: 
- 每个API路由只处理一个业务操作
- 组件按功能拆分，如CollectionCard、PriceDisplay

**Dev**: 这有助于代码维护和测试。

**2. 开闭原则 (OCP)**

对扩展开放，对修改关闭。

**应用**:
- 使用配置文件管理IP系列数据
- 估价策略可通过插件扩展

**3. DRY原则 (Don't Repeat Yourself)**

代码复用，避免重复。

**应用**:
- 共享组件库（Button、Input、Card等）
- 统一的API客户端
- 公共工具函数

**4. 安全第一原则**

安全作为架构设计的基础考量。

**应用**:
- 所有API端点需认证
- 敏感数据加密存储
- HTTPS强制使用

## 第四轮对话：分层架构

### 话题：系统分层设计

**Architect**: 系统采用经典的三层架构设计：

**层次 1: 表现层 (Presentation Layer)**

```
┌─────────────────────────────────────────┐
│         表现层 (Next.js App Router)     │
├─────────────────────────────────────────┤
│ • Page Components (页面组件)            │
│ • Server Components (服务端组件)        │
│ • Client Components (客户端组件)        │
│ • Middleware (中间件：认证、日志)        │
│ • Error Handling (错误处理)              │
└─────────────────────────────────────────┘
```

**职责**: 
- 接收用户请求
- 渲染页面
- 数据验证和格式化

**DesignArchitect**: 前端技术栈确认：Next.js 14 + React 18 + TypeScript + Tailwind CSS

**层次 2: 业务逻辑层 (Business Logic Layer)**

```
┌─────────────────────────────────────────┐
│      业务逻辑层 (API Routes + Services) │
├─────────────────────────────────────────┤
│ • API Routes (API路由)                  │
│ • Service Classes (业务服务)            │
│ • Business Rules (业务规则)              │
│ • External API Clients (外部API客户端)   │
└─────────────────────────────────────────┘
```

**职责**:
- 实现核心业务规则
- 数据处理和转换
- 调用外部服务

**层次 3: 数据持久化层 (Data Access Layer)**

```
┌─────────────────────────────────────────┐
│      数据持久化层 (Supabase)            │
├─────────────────────────────────────────┤
│ • PostgreSQL Database (关系数据库)      │
│ • Supabase Auth (认证服务)              │
│ • Row Level Security (行级安全)         │
│ • Realtime Subscriptions (实时订阅)     │
└─────────────────────────────────────────┘
```

**职责**:
- 数据库操作
- 数据查询和存储
- 认证授权

### 话题：AI估价模块

**Architect**: AI估价模块是核心功能，设计如下：

**功能**:
- 调用DeepSeek API生成估价
- 本地预设数据缓存
- 估价结果存储

**估价流程**:

```
用户请求估价
    │
    ▼
查询本地预设数据
    │
    ├─ 命中缓存 → 直接返回预估价格
    │
    └─ 未命中 → 调用DeepSeek API
                    │
                    ▼
               构建Prompt（包含款式信息、市场数据）
                    │
                    ▼
               解析AI响应
                    │
                    ▼
               缓存结果
                    │
                    ▼
               返回估价报告
```

**Dev**: AI调用的错误处理机制？

**Architect**: 错误处理策略：
1. **超时处理**：5秒超时，降级返回预设价格
2. **API失败**：使用本地缓存的最新估价
3. **无数据**：提示用户手动估价
4. **限流处理**：队列化请求，控制并发

## 第六轮对话：性能设计

### 话题：缓存策略

**Architect**: 缓存是性能优化的关键：

**缓存分层**:

```
L1: Next.js 缓存 (ISR/SSG)
    └─ 静态页面、公共数据
       ├─ 首页、登录页
       └─ IP系列列表

L2: Vercel Edge Cache
    └─ CDN边缘缓存
       ├─ 静态资源（JS/CSS/图片）
       └─ API响应缓存

L3: Supabase 查询缓存
    └─ 数据库查询结果
       ├─ 价格数据
       └─ 用户收藏列表
```

**缓存策略**:

| 缓存类型 | 更新策略 | TTL | 适用场景 |
|----------|---------|-----|----------|
| 页面缓存 | ISR重新验证 | 1小时 | 公共页面 |
| API缓存 | 主动失效 | 5分钟 | 收藏列表 |
| 价格数据 | 定时更新 | 24小时 | 预设价格 |

### 话题：数据库优化

**Dev**: 数据库性能如何保证？

**Architect**: 数据库优化策略：

**索引策略**:

```
主表索引:
├─ 主键索引 (id)
├─ 用户索引 (user_id)
├─ 款式索引 (ip_series, model_name)
└─ 复合索引 (user_id, created_at DESC)
```

**查询优化**:
- 使用参数化查询防止SQL注入
- 避免 SELECT *，只查询需要的字段
- 使用分页（每页20条）
- 利用Supabase的实时订阅减少轮询

## 第七轮对话：安全设计

### 话题：认证与数据安全

**QA**: 安全设计是测试的重点，请详细说明。

**Architect**: 安全架构设计：

**认证安全**:
- 密码安全：使用bcrypt哈希，盐值随机
- Token安全：JWT短有效期（1小时），Refresh Token机制
- 会话管理：HttpOnly Cookie存储

**数据安全**:

| 安全措施 | 说明 | 实现 |
|---------|------|------|
| 传输加密 | HTTPS/TLS | Vercel自动配置 |
| 数据加密 | 敏感数据加密 | AES-256 |
| 字段掩码 | 敏感字段显示 | 仅显示部分 |
| 行级安全 | 数据隔离 | Supabase RLS |

**API安全**:
- 速率限制：每用户每分钟100次请求
- 输入验证：所有输入都必须验证
- CORS设置：限制跨域请求来源

**常见攻击防护**:

| 攻击类型 | 防护措施 |
|---------|----------|
| SQL注入 | 参数化查询、Supabase ORM |
| XSS攻击 | React自动转义、CSP头 |
| CSRF攻击 | Same-Site Cookie、Token验证 |
| DDoS攻击 | Vercel内置防护、速率限制 |
